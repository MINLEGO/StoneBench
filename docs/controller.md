# Minecraft controller and MCP contract

Each attempt uses its own fresh server process and directory. Start two processes for two attempts; never reuse a world directory for a new attempt. `start_attempt` fails if that server already has an attempt. Its immutable `stonebench/attempt.json` records geometry, environment, preparation and identity. Every operation is appended to `stonebench/operations.jsonl`.

Production catalog: `start_attempt`, `describe_task`, `read_blocks`, `read_region`, `read_artifact`, `compare_traces`, `describe_blocks`, `describe_block`, `modify_blocks`, `advance`, `transition`, `declare_input`, `prepare_input`, `act_input`, `describe_rules`, `check_geometry`, `create_checkpoint`, `list_checkpoints`, `restore_checkpoint`, `verify_checkpoint`, `verification_status`, `cancel_verification`, `verification_snapshot`. Independent-copy verification is described in [the verification contract](verification.md). Checkpoint restore uses the owning restart supervisor and exposes a tick-0 loaded-state comparison before useful simulation; see [checkpoint contract](checkpoints.md). Streamable HTTP endpoint: `http://127.0.0.1:18765/mcp`. MCP protocol versions 2025-11-25, 2025-06-18 and 2025-03-26 are supported; initialization, notifications, tool discovery/calls and ping use JSON-RPC. Responses use JSON rather than the optional SSE stream; GET/DELETE return 405. Local Origin headers are validated. Server console logs are separate from MCP. See the [MCP transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

```json
{"name":"start_attempt","arguments":{"task_id":"2x2-volume","budget_tokens":100000}}
{"name":"read_blocks","arguments":{"positions":[{"x":1024,"y":80,"z":1024}]}}
{"name":"advance","arguments":{"ticks":20}}
```

Task ids are `2x2`, `3x3`, `4x4`, `5x5` with `-volume` or `-speed`. Budget is caller supplied; omit it or use null when unavailable. It is not inferred to be zero. The immutable passage has origin (1024,80,1024), horizontal +X, vertical +Y, normal +Z; expected frame lists its coordinates. No blocks of physical encadrement are pre-built.

The initial ticking-ready chunk (64,64) covers an air region. It is an initial preparation scope, not a boundary of valid constructions. Reads outside prepared chunks return an explicit validation error. Reads are bounded to 256 coordinates, and callers must split larger requests; there is no silent truncation. `Controller.prepareChunks` is the server-thread extension seam for later placement/observation tools to expand the relevant set **before mutations**. Its preparation phase concludes only when every relevant chunk passes all three vanilla readiness checks. Later tools must resume their action after preparation; do not report placement success merely because preparation ended.

Operations enter a queue and all world access runs in `beforeTick`/`afterTick` on the server thread. An active operation owns the world until its result is recorded; concurrent requests wait. The vanilla tick manager advances one game tick per hook. Native sprint is the default for `advance`, `act_input` and `transition`, following the real unit/sprint differential fixtures in issue #9; no artificial 20 TPS cap is applied. `-Dstonebench.tickExecution=unit` retains the nominal 20 TPS reference. Every operation records execution mode/backend and separates actual game ticks from measured wall time/TPS. This evidence concerns the pinned vanilla fixture scope, not arbitrary mods/entities. Preparation ticks and useful simulation ticks are separate. Readiness requires `shouldTickBlocksInChunk`, the ticking future, and a chunk level at least BLOCK_TICKING; a loaded chunk alone is insufficient. Loss of readiness revokes vanilla's already-computed tick permission, freezes the world and reports partial execution. Ordinary operations have a 420-second infrastructure safety limit, separate from the requested 1..6000 ticks. `transition` instead observes up to 36000 real game ticks, with a distinct 2400-second process safety deadline (about 30 minutes of simulation at 20 TPS). It reports `terminated`, `limit_reached` or `indeterminate`, cause and real tick count; see [the rest contract](rest.md). Queue waiting does not consume this limit.

Each tool returns MCP `structuredContent` and equivalent text, with `operation_id`, `operation`, `attempt_id`, `phase`, `status`, `ticks_executed`, `simulation_ticks`, `preparation_ticks`, `world_time`, `frozen`, and `mutated`. Error kind is `validation`, `unsupported` or `infrastructure` with a code and diagnostic. `mutated=true` means effects may have happened: a failed start needs a fresh process/directory, and a failed advance preserves its actual executed count. Disconnecting does not cancel an already accepted operation; consult the operation journal before retrying. Transport failure or process death does not fabricate a completed domain result.

Pinned environment: Minecraft 1.21.11, Yarn 1.21.11+build.3, Fabric Loader 0.19.5, Loom 1.14.10, Gradle 9.2.1, Java target 21. The launch scripts default to installed JDK 21.0.12. Seed 731928, flat air generator, no structures, no players, view/simulation distance 2, no automatic empty-server pause. Effective random tick speed 0, mob spawning false and weather advance false are set through vanilla rules and recorded. All eight tasks use these settings.

`-Dstonebench.test=true` adds isolated fixture/fault tools solely for disposable integration servers. They never appear in the production catalog. Removing forced chunk tickets exercises real readiness loss; no readiness boolean is mocked. Ordered construction and inventory tools are described below. Typed NBT, per-tick observations and diffs are available as recoverable artifacts; see docs/observation.md. Checkpointing, conformity and Inspect are subsequent tickets.

## Ordered construction lots

`describe_blocks` takes no argument and returns only `{"catalog":[...]}`: the 70 complete ids of the construction catalogue, unique, in the fixed order of [the source list](blocs-a-prendre-en-charge.md), with no property, inventory or capability detail. **This format is incompatible with earlier versions**, which returned one object per block (`id`, `configurable`, `computed`, `inventory_slots`) plus `coverage` and `inventory_contract`; clients must now call `describe_block` for those. `describe_block` takes one exact `id` and returns `id`, `configurable` and `computed` property values (always strings), `inventory_slots`, the `coverage` note, an `inventory_contract` when the block has slots, and the existing observation-limit annotations that apply to it (hopper cooldown/last tick, `runtime_coverage` for block-entity blocks). An unknown or withdrawn id (for example `minecraft:stone`, which this catalogue no longer contains) returns `kind=unsupported, code=unsupported_component`, never the catalogue; the same code is returned by `modify_blocks` and `declare_input`. Both tools are reads: no mutation, no time advance, and both are allowed while a verification is running. Coverage is a construction API limit, not a conformity rule and not evidence of rest or faithful restoration: new block-entity blocks (beacon, player head, furnace, shulker box, chests) keep the existing observation, rest and restoration limits until their coverage is established. Raw block states, NBT, data components, piston progression, power, locks, cooldowns and internal timestamps cannot be injected; `player_head` has no custom profile. Typed internal block-entity observation is read-only; see docs/observation.md for observed runtime fields and explicit certification limits. No measured token saving is claimed: no archived before/after comparison of the responses exists.

```json
{"name":"modify_blocks","arguments":{"blocks":[{"x":1024,"y":80,"z":1024,"block":"minecraft:redstone_wire"},{"x":1024,"y":79,"z":1024,"block":"minecraft:quartz_block"}],"notify_neighbors":true}}
{"name":"modify_blocks","arguments":{"blocks":[{"x":1026,"y":80,"z":1024,"block":"minecraft:chest","parameters":{"facing":"north"},"inventory":[{"slot":0,"item":"minecraft:diamond","count":7}]}],"notify_neighbors":false}}
```

Lots contain 1..256 placements, with no silent truncation. Duplicate coordinates are rejected. Air deletes a block. Parameter values use catalog strings; inventories use unique slots and registered vanilla items with counts within item/container stack limits and vanilla slot validity. An inventory supplied in a lot replaces the entire inventory (an empty array clears it); omitting it preserves a retained block entity's inventory or leaves a newly created one empty. Replacing an inventory block with another block removes its block entity and does not spill item entities into the construction.

Validation examines the final geometry through a server-thread read-only placement view, so an ordinary support may occur later in the submitted list (a support whose shape depends on resolution, such as stacked scaffolding, must be submitted first). Every placement uses the block's vanilla `getPlacementState`, with configured player-facing/attachment information, and `canPlaceAt`; the submitted position is empty in that view during placement, avoiding accidental slab merging with the planned block itself. No world block or inventory changes until the entire lot is valid. Each placement is resolved in submitted order and later entries see earlier ones in their resolved state (for example a scaffolding stacked on a scaffolding of the same lot).

The controller prepares each placement chunk and its immediate neighboring coordinates, retaining every previously prepared chunk. Extension preparation loads forced chunks while the world remains frozen, and resumes placement only after vanilla readiness. It advances no gameplay or preparation-world ticks. The initial empty-world preparation retains its separately recorded ticks. This preparation scope is not a boundary imposed on construction or conformity.

Installation uses vanilla `FORCE_STATE_AND_SKIP_CALLBACKS_AND_DROPS` (816): all geometry is installed, then all inventory contents, before state callbacks or neighbor propagation. Inventory `markDirty` calls normally update comparators, so comparator updates are suppressed only during installation and transmitted during the ordered notification phase. With `notify_neighbors=true`, each submitted coordinate is processed in order: old-state replacement callback when applicable (including rails), new-state added callback for a changed state, neighbor notification, comparator notification only when the new state has comparator output, then vanilla shape propagation. Cascades caused by one root run naturally before the next root. Same-block property changes retain the new-state callback. With `false`, callbacks and neighbor/comparator propagation are suppressed; advancing later is explicit and does not synthesize a missed notification phase.

Construction coverage beyond ordinary placement:

- **Waterlogging.** Every catalogue block that owns the vanilla `waterlogged` property (derived from the registry, not from a list) publishes it as `configurable` with `"true"`/`"false"`; other blocks refuse it. Water is installed with the block; fluid ticks and updates follow the notification contract above and explicit time advance, so a waterlogged state set with `notify_neighbors=false` schedules no fluid tick until a later notification. Other electrical or internal states are not generalised from this exception.
- **Free water.** `minecraft:water` places a source. Levels and flow are computed by Minecraft with vanilla ticks; no level parameter exists and `modify_blocks` never advances time.
- **Doors.** An `oak_door` or `iron_door` entry names the lower half; both coherent halves are created. Both cells, support, vertical/world limits and coordinate conflicts with any other entry or generated half are validated before any mutation, and `half` cannot be forced. Both halves are installed before the notification phase, and notifications run lower half then upper half, immediately after each door's submitted position, so `notification_order`, `blocks` and `placements_applied` count two entries per door. `open` is configurable for `oak_door`, `oak_trapdoor` and `oak_fence_gate` only; iron door and trapdoor open state stays derived. `composter` accepts `level`.
- **Withdrawn ids.** Blocks absent from the 70-block catalogue are no longer constructible, but worlds, traces and checkpoints that contain them are still read normally.

`read_blocks` keeps its original state string and additionally returns the registry block id, every actual state property as a string, and occupied inventory slots (`slot`, `item`, `count`). Success returns actual post-notification block records and the submitted `notification_order`. Construction errors after mutation return `mutated=true`, actual block/inventory records and recovery guidance; this is not transactional rollback. Repair with another validated lot, or restore a checkpoint when that tool becomes available. No tick is inserted after placement. Production servers expose no fault or raw-state fixture tools. Disposable test servers additionally record actual state callbacks and neighbor/comparator calls, their root index and whether the entire geometry, configured parameters and inventories existed when each hook ran.
`declare_input`, `prepare_input` and `act_input` expose vanilla lateral inputs. See [input contract](input.md) for adapter ownership, phase and preservation guarantees.

Sourced regular DOOR snapshot diagnostics are documented in [geometry](geometry.md), with the frozen operational [rule table](rules/regular-door.md). They advance no ticks and do not replace the functional alpha verifier or dynamic measurement tools.
