# Inspect harness

Issue #14 uses Inspect's native `react()` loop. A single-call Agent model adapter checks the phase/budget then delegates generation to Inspect's `Model.generate`; it never implements an inference loop. MCP tools retain their discovered schemas and descriptions, wrapped at the local execution boundary. An irreversible per-attempt phase object governs the wrapper, independently of Minecraft restoration/context and verification copies. Unknown tool names are excluded from the production allowlist.

Integration seam: no Controller/McpHttp change is needed. Existing MCP calls `list_checkpoints`, `verify_checkpoint`, `verification_status`, `cancel_verification`, and immutable evidence support explicit selection and independent-copy scoring. `submit_checkpoint(checkpoint_id)` is a harness tool, not a world operation. It validates existence before retaining the exact ID; the scorer verifies only that ID, never saves the current state or chooses a different checkpoint. No choice yields `no_submission`.

Inspect is pinned to 0.3.278, MCP SDK to 1.26.0. Provider usage is authoritative: `total_tokens` includes input and output; reasoning is part of completion and is never added again. A missing usage result poisons total availability for the whole attempt; the known subtotal remains separately labelled. Missing optional reasoning/cache/cost fields remain null. Inspect also records its own usage/events and token limit. The adapter's ledger attributes each reported call to construction/finalization and preserves provider totals without fabricating zero usage.

## Reserve and calibration

Configuration requires total budget, construction completion bound, final visible-output allowance, final reasoning allowance, margin and final-call safety count. Final completion bound = visible output + reasoning allowance, since the provider counts both as completion. No provider-specific reasoning effort/max_tokens field is inferred from model advertising. Preserve provider reasoning behavior; paid provider calibration belongs to #15 and needs user authorization.

Before generation, forecast one construction call = current context estimate + construction completion bound. Final reserve = estimated context of the last call + final visible output + counted reasoning allowance + margin. If used + forecast + reserve would exceed total, switch before that construction call and explicitly request an existing checkpoint ID. The forecast is an estimate, not paid usage. It includes messages and tool schemas, and uses UTF-8 byte count as a conservative text heuristic with documented overhead/margin; model/provider chat templates, hidden tokens, image inputs and unknown tokenizer behavior require actual calibration. Alpha text-only input is enforced. Retain context estimates and actual usage per call for their comparison so #15 can calibrate with the precise model/provider rather than a fake universal token guarantee.

Finalization tool calls can expand the next input context; recalculate before every call. Completion outputs are bounded through Inspect GenerateConfig `max_tokens`, including reasoning. Already running provider calls cannot be stopped at an exact total; record observed overshoot and then stop generation. The first missing usage triggers finalization and a finite final-call cap, while used/remaining totals remain unavailable.

## Validation and limits

The scripted provider implements Inspect's public ModelAPI and returns controlled ModelOutput/ModelUsage; it performs no HTTP inference. Inspect's native react loop discovers and executes actual MCP tools on disposable Minecraft servers. The complete suite includes reserve transition, valid/invalid refused world tools, asynchronous copy consultation/cancellation, source conservation, explicit selection of an older nonconforming checkpoint rather than the newest/conforming one, submission during an active copy, invalid/no selection, unavailable usage, long reasoning and provider overshoot. A fresh second server exercises harness initialization. See [exportable evidence](evidence/issue-14/README.md).

Inspect can raise its native token limit after recording a completed ModelEvent and before Model.generate returns. The adapter recovers the actual completed usage from the public [transcript API](https://inspect.aisi.org.uk/reference/inspect_ai.log.html), records the observed overrun, then rethrows the native [LimitExceededError](https://inspect.aisi.org.uk/reference/inspect_ai.util.html). Inspect's counter and limits remain authoritative and active. No adapter call bypasses this accounting.

The test budget is 300,000 tokens, with 4,000 construction completion tokens, 4,000 final visible tokens, 20,000 final reasoning tokens, 2,000 margin and up to 120 final calls for controlled polling. These numbers are test configuration, not a campaign recommendation. A first reported 260,000-token call causes the following call to enter finalization; the mock long-reasoning case reports another 52,000 tokens including 49,000 reasoning tokens and records 312,000 total rather than double-counting reasoning. A separate first-call overshoot records 390,000. Missing usage stays null despite Inspect's own aggregate counters.

Each native MCP result is retained with a hash. Results over 16 KiB are returned as explicit references; read_harness_artifact recovers bounded 4 KiB byte pages, avoiding silent truncation. Model completion limits depend on provider compliance; observed bound breaches are logged. Invalid arguments/unknown tools rejected by Inspect appear in the native transcript; valid tools rejected by the phase guard additionally appear in events.jsonl. Full verification outcomes and independent geometry/timing measurements are retained in scorer metadata; its binary conformance field does not combine volume and time into a synthetic score.

This baseline validates the native loop, controlled usage accounting and actual Minecraft effects. It does not validate a paid model's tokenizer, hidden input overhead, reasoning allocation, provider routing or task-solving ability. Calibrate those with the exact provider in #15 after numerical budget/cost authorization. No paid inference was authorized or executed. The harness uses the controller's sprint defaults and independent verification watchdogs; it adds no fixed 20 TPS cap or whole-verification wall timeout.

The #13 integration retains the complete measurement report in scorer metadata. Revalidation asserts dynamic_volume stays indeterminate with value=null, distinct minimum/maximum envelopes and gaps; observed upper volume is not promoted to exact volume. Opening and closing remain separate game-tick measures (6gt repeater reference, 4gt direct diagnostic on the canonical fixture), including interaction, signal, movement and rest provenance. No volume/time objective is fused by the harness. See the integrated #13 evidence alongside the original baseline archive.

## Local audit

The scorer still starts and awaits the selected checkpoint's verification through MCP, but its result comes from the complete local audit (`stonebench/verifications/<request_id>/completed.json` under the `server_root` given to `stonebench_task`; `app/harness/audit.py`). It requires the exact local `attempt_id`, the request frozen by the controller, the checkpoint manifest hash and the selected checkpoint to agree, and the MCP status to agree on verdict, measurements and criteria. An absent, unreadable or mismatched audit yields `audit_error` and score 0; a conforming verdict is positive only if the audit also has provenance, source-bearing criteria, boundary snapshots (integer `world_time`) with operations, per-transition measurements with their sources and timing provenance (an unmeasured volume or time must state its gaps, so the indeterminate `dynamic_volume` above stays acceptable) and a preserved working construction. A malformed audit is an `audit_error`. Scorer metadata keeps `verification` (MCP status) and adds `audit` (identity, path, SHA-256, completeness) and `audit_positive`. With no `server_root`, nothing can score positively. `tests/audit.py` covers binding and completeness without Minecraft; `tests/harness_inspect.py` re-reads the audit from files alone.
