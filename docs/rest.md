# Observed rest and transition contract (issue #9)

`transition` advances unit vanilla ticks until observed rest, an indeterminate memory/coverage result, or its simulation bound. Arguments are `max_ticks` (optional, defaults to 36000, 1..36000) and `trace` (optional boolean). Ordinary `advance` remains limited to 6000. The dedicated server stays frozen between operations. A 2400-second process safety deadline is separate from simulation limits: reaching it is an infrastructure error, never a tick-limit verdict. At 20 TPS, a real 36000-tick transition needs about 30 minutes without sprint.

The report `transition.status` is `terminated`, `limit_reached`, or `indeterminate`; it includes actual relative `tick`, `causes`, `last_movement_tick` and nullable `recognition_tick`. The movement timestamp records relevant block changes (including successful intra-tick writes); it does not define the reference's opening-time rule. Recognition requires two consecutive identical complete relevant block records, no relevant activity this tick, no scheduled block/fluid or block-event queue, and no mobile piston. The queue retains absolute deadlines, priorities and order. Snapshot clocks remain absolute; they are separate from the block execution state, never reset. Inventories, typed NBT, serialized temporal fields and runtime memory are compared exactly, without field deletion or normalization.

Reads alone and unsuccessful/no-op write requests are not activity. Other observed events are relevant even if the final visible state returns to its previous value. Events at declared external input-adapter positions are counted separately as `external_input_events`; both external and internal effects still prevent a false pause, and all their future deferred work remains relevant. Input preparation and invocation use issue #8's vanilla phase contract.

Coverage must remain observed and ticking-ready. Once lost, identical later data cannot repair a missing observation. Chunk availability errors belong to execution infrastructure. No positive rest follows missing queue/runtime observations. The production instrumentation still reports `certification=false`; observed rest on the covered components does not certify a complete regular DOOR, arbitrary JVM memory or faithful checkpoint restoration.

The component proof scope is the immutable issue #1 fixtures: ordinary non-entity blocks, piston movement and chest inventory. Other block entities remain indeterminate until their nonserialized memory and behavior are established. Hoppers are observed, not banned: cooldowns and possible transfers keep the transition running; once these are inactive, `last_tick_time` yields `indeterminate`, even with unchanged inventories in empty or locked cases. No new normalization is implemented. Broadening this rule requires exact-version differential behavior, interactions and restoration evidence, not a cosmetic equality test.

`tests/transition.py` is the real Minecraft/MCP fixture suite; `RestChecks` adds focused negative controls for pure classifier branches. Test-only fixture tools reproduce prototype #1 geometry and its cooldown setup on disposable `stonebench.test=true` servers. Their direct field setup is not a production construction API. Fixtures execute genuine vanilla ticks and capture genuine typed runtime values.
