# Observed rest and transition contract (issue #9)

`transition` advances individual vanilla game ticks until observed rest, an indeterminate memory/coverage result, or its simulation bound. Arguments are `max_ticks` (optional, defaults to 36000, 1..36000) and `trace` (optional boolean). Ordinary `advance` remains limited to 6000. The dedicated server stays frozen between operations. A 2400-second process safety deadline is separate from simulation limits: reaching it is an infrastructure error, never a tick-limit verdict. Wall-clock time and measured throughput are reported separately from game ticks. The explicit unit reference takes about 30 minutes for 36000 ticks at nominal 20 TPS.

The report `transition.status` is `terminated`, `limit_reached`, or `indeterminate`; it includes actual relative `tick`, `cause`, `causes`, `last_movement_tick` and nullable `recognition_tick`. The movement timestamp records relevant block changes (including successful intra-tick writes); it does not define the reference's opening-time rule. Recognition requires two consecutive identical complete relevant block records, no relevant activity this tick, no scheduled block/fluid or block-event queue, and no mobile piston. The queue retains absolute deadlines, priorities and order. Snapshot clocks remain absolute; they are separate from the block execution state, never reset. Inventories, typed NBT, serialized temporal fields and runtime memory are compared exactly, without field deletion or normalization.

Reads alone and unsuccessful/no-op write requests are not activity. Other observed events are relevant even if the final visible state returns to its previous value. Events owned by declared external input-adapter positions are counted separately as `external_input_events`. Scheduled callbacks are classified as external only when their scheduled block type matches the real captured block, orientation and active declared button/repeater mode; callbacks at floors/supports and wrong-type schedules remain internal. Both external and internal effects still prevent a false pause, and all their future deferred work remains relevant. Input preparation and invocation use issue #8's vanilla phase contract.

Coverage must remain observed and ticking-ready. Once lost, identical later data cannot repair a missing observation. Chunk availability errors belong to execution infrastructure. No positive rest follows missing queue/runtime observations. The production instrumentation still reports `certification=false`; observed rest on the covered components does not certify a complete regular DOOR, arbitrary JVM memory or faithful checkpoint restoration.

The component proof scope is the immutable issue #1 fixtures: ordinary non-entity blocks, piston movement and chest inventory. Other block entities remain indeterminate until their nonserialized memory and behavior are established. Hoppers are observed, not banned: cooldowns and possible transfers keep the transition running; once these are inactive, `last_tick_time` yields `indeterminate`, even with unchanged inventories in empty or locked cases. No new normalization is implemented. Broadening this rule requires exact-version differential behavior, interactions and restoration evidence, not a cosmetic equality test.

`tests/transition.py` is the real Minecraft/MCP fixture suite; `RestChecks` adds focused negative controls for pure classifier branches. Test-only fixture tools reproduce prototype #1 geometry and its cooldown setup on disposable `stonebench.test=true` servers. Their direct field setup is not a production construction API. Fixtures execute genuine vanilla ticks and capture genuine typed runtime values.


## Execution cadence

Native `ServerTickManager.startSprint(N)` is the default for `advance`, `act_input` and `transition`, after 56 exact real comparisons against the unit reference on the same pinned version. The controller observes every real end-of-tick, stops on the observed game-tick count or earlier rest/error, and cancels sprint before freezing. The initial dispatch may have a zero world-time delta because vanilla has already cached its frozen permission; it is not an observed tick and triggers no interaction. Input activation stays in `before_world_time` at the first actual tick. Preparation on a populated construction remains frozen.

`execution` records `mode`, `backend`, actual `game_ticks`, `wall_seconds`, `measured_tps` and the nominal tick rate; the latter does not cap a native sprint. `environment.tick_execution` records the selected mode. `-Dstonebench.tickExecution=unit` is the reproducible reference option; `sprint` is the default native backend. Subsequent checkpoint/verification/campaign callers should reuse the same controller tick path and record comparable mode parameters. These modes alter cadence, not the game-tick unit or the 6000/36000 API bounds.

`tests/transition_sprint.py` uses two independent fresh worlds. Its test-only initial preparation is 120 real ticks on the empty world, recorded as preparation, so absolute clocks begin equal without resetting them. It resolves artifact UUIDs into their complete contents and compares all observation/state/event fields, exact runtime/NBT/inventories, queue deadlines/priorities/order and absolute clocks. It covers piston/chain opening/closing, hopper transfers and inactive memory, observer clock, six native input cycles, one-tick advances, early rest, bounded transition and real readiness failure. This is fixture evidence, not a universal equivalence theorem for every entity or mod.
