# Checkpoint verification on independent copies

`verify_checkpoint(checkpoint_id)` names an explicit immutable checkpoint. Optional `frame_min_z`/`frame_max_z` follow the existing fixed-passage geometry contract. The owning `checkpoint_server.py` supervisor is required; an ordinary server refuses this tool before changing anything. The MCP result immediately contains `verification.status=running` and `request_id`. Poll `verification_status(request_id)` for progress and the immutable final report, or call `cancel_verification(request_id)`. A client disconnect does not cancel an accepted job.

The job owns and freezes the working world for the entire verification. It writes a request containing checkpoint identity/manifest hash and the exact working raw snapshot, then polls an atomic worker result without game ticks. Mutations, simulation, restores and reads that expand coverage are refused while it runs; bounded status, cancellation and immutable evidence reads remain responsive. The controller compares the exact working snapshot, including absolute clocks and coverage, after completion. A mismatch revokes conformity and reports infrastructure failure. Refused checkpoints, worker errors and interrupted workers do not restore, replace or advance this world.

The active job is published only after its request is written atomically. A publication IO failure reports `verification_publication_failed` and leaves no active job or working-world lease; the failed candidate remains diagnostic evidence. Cancellation accepted before final controller publication vetoes a positive verdict, including the worker/result publication race. If an individual phase stalls after cancellation or its watchdog, the supervisor first stops its owned JVMs, then publishes an infrastructure fallback so a stalled I/O thread cannot retain the working lease. A later detailed worker result is retained separately as `late-worker-result.json`.

There is no cumulative verification wall timer. The supervisor publishes owner liveness every second; 90 seconds without it produces `owner_heartbeat_lost`, an infrastructure result, never a construction fault. Progress means starting or completing a finite phase (copy/hash, boot, tool or archive/comparison), identified by a sequence counter. Copy/hash and non-transition tools have separate 420-second watchdogs, each boot has 180 seconds, and each transition retains the controller's 2400-second watchdog plus bounded HTTP transport cleanup. The supervisor checks the current phase deadline independently of its heartbeat. It does not require an otherwise healthy long transition to finish within 90 seconds. Cancellation stops only owned copy processes, retains their data and publishes a nonconformant infrastructure report; it never cancels the working JVM. Lost-owner copies remain retained for recovery with PID/session-lock guards.

The supervisor prepares two distinct directories/processes/MCP ports/game ports: repeater and direct. Each has independent world, artifacts, logs, Fabric cache, libraries and JVM. Source dependencies are only copied. Checkpoint file-set/hash, manifest identity and attempt ownership are validated before copying, after copying and after the protocol. Each independent world is checked against the checkpoint's world hashes before launch, then the existing frozen boot path performs exact loaded-state comparison at tick 0. Preparation must execute zero game ticks and preserve construction; a failed or incomplete tick-0 comparison forbids useful simulation. The supervisor retains its OS lease and child PID/session-lock guards. Worker owners stop only processes they created, before releasing their leases.

The verifier validates the closed state0 geometry, lateral live input, checkpoint rest and covered memory. An incomplete door receives diagnostics without conformity. Repeater preparation uses `prepare_input` and compares the complete construction before/after. The existing adapter tool keeps its inactive-device prerequisite. If the checkpoint driver is active, the copy alone performs a traced vanilla interaction to deactivate it, prepares its adapter, then performs a traced interaction back to the original active state. Exact construction equality with state0 is required before measured cycles; preparation operations, ticks and absolute clocks are archived separately. A checkpoint already using a repeater can similarly prepare direct mode by removing only its external adapter blocks, installing/declaring the original supported wall device through the ordinary construction/input tools and proving exact state0 return. No powered state or queue field is injected. Each open/closed transition calls `transition(interact=true,max_ticks=36000,trace=true)`: vanilla interaction occurs in its original before-world-time phase and counts within that same transition, with no extra action tick outside the bound. The native sprint backend is reused; `stonebench.tickExecution=unit` remains the reference.

After each repeater cycle the closed construction is compared to state0. The verifier stops on the first exact return, or after five cycles. Every executed boundary must satisfy its mandatory criteria; an invalid opening remains a failure even if a later closure matches. A distinct direct copy starts from exactly the same tick0 checkpoint and runs one cycle; its open and closed construction states are compared to the corresponding first repeater cycle. Durations may differ. The derived maximum is twelve transitions times 36000 = 432000 ticks; there is no additional global game-tick quota. Per-transition process watchdogs, frozen preparation/boot watchdogs and working-controller infrastructure watchdogs are separate from simulation limits.

Construction comparison retains all block properties, inventories, typed NBT, runtime data and ordered block/fluid/event queues. Global clocks and the validated external adapters are archived separately. The input support block stays construction/wiring. Empty air sampling records use implicit air so expansion of the tracked set alone does not change construction; a nonair-to-air difference is retained. No numeric type, NBT list ordering, internal timing field, queue absolute deadline, priority or sub-tick order is discarded. Queue-relative normalization is not implemented. Raw snapshots and complete per-tick artifacts retain original clocks and adapter records regardless of the comparison partition.

Standalone `check_geometry.geometry_status` remains indeterminate. Verification composes its individual criteria with real transition/rest and hash-validated contiguous tick/intratick traces in the instrumented alpha scope. Open regular-arrangement/material evidence refers to the closed frame of the same mechanism. Non-quartz substitution remains indeterminate without its required behavioral proof. Covered memory limits from checkpoints/rest remain mandatory: hopper JVM timing, torch burnout history and unknown block-entity memory cannot silently become conformant. This bounded protocol does not certify arbitrary JVM state or indefinite community-record reliability.

Reports include protocol/checkpoint/provenance, source-bearing criteria with expected/observed/status/diagnostic, all boundaries, cycle count, stop cause, first state discrepancy, worker restoration identity, original operation/trace references, transition ticks and wall time. Infrastructure errors are distinct from observed construction failures. Every mandatory indeterminate criterion prevents conformity. Record criteria remain not verified. `measurements` retains transition/rest timestamps and references for issue #13; dynamic volume and source-defined movement-end timing are not yet verified. Issue #14 can call this tool during finalization without mutating the work attempt and submit the explicitly named checkpoint.

Each request retains its request/result/completed report and both complete worker roots under `stonebench/verifications/<request_id>/`. Useful copies are not deleted on success or failure. Production supervisors accept explicit `--verification-mcp-port` and `--verification-game-port` base ports; reserve two adjacent ports of each kind for a verification. The test launcher reserves separate groups for its two independent work attempts. Ports already in use produce an infrastructure diagnostic; another process is never stopped to make room.

Test-only controls can inject real state mutations on copies after a vanilla boundary and re-establish rest inside that boundary's remaining 36000-tick allowance. The configuration/mutation tools exist only when `stonebench.test=true`; production workers refuse a test plan. These controls test the delivered MCP recurrence/verdict/comparator flow (cycle2, no return5, bad opening, block/inventory/internal-field differences), not a claim that the positive vanilla circuit naturally has a two-cycle recurrence. Exact injected operations and post-fault traces are retained.
