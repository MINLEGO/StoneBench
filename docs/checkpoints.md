# Immutable rest checkpoints (issue #10)

`create_checkpoint`, `list_checkpoints` and `restore_checkpoint` are production MCP tools. The dedicated controller serializes their operations on the server thread. Real-server evidence and exact limitations are archived in [issue #10 evidence](evidence/issue-10/README.md).

`create_checkpoint` has no argument. It requires the last real `transition` to have returned `terminated`, the world to be frozen between ticks, complete ready observations and the exact same state/clocks as that rest proof. A merely frozen world, stale proof, moving piston, pending event, indeterminate hopper or unsupported runtime memory is rejected. Door conformity is not a prerequisite: an unfinished mechanism can be saved. The controller flushes Minecraft's save on its server thread and copies the whole world, excluding `session.lock`. Source-before, copied and source-after file hash maps must agree. A partial copy never becomes a published ID.

`list_checkpoints` retains every published UUID and returns immutable provenance, creation time, per-file SHA-256 and manifest SHA-256. Each checkpoint contains `world/`, `context.json`, `state.json`, `manifest.json` under `stonebench/checkpoints/<UUID>/`. A source world update does not update the checkpoint. Metadata is controller-owned immutable data; ordinary corruption is detected by exact file-set/hash verification, not treated as a valid partial checkpoint. External exports should retain the manifest hash to establish provenance independently of the local filesystem.

`restore_checkpoint(checkpoint_id)` is explicitly a mutation of the same attempt, including its clock. It verifies hashes and attempt ownership, writes an atomic `stonebench/restore-request.json` and returns `restart_required`. The owning supervisor then stops only its own Minecraft process, waits for exit, verifies the checkpoint again against the request's manifest hash, stages a whole-world copy, and swaps world directories. The old world remains a backup until successful boot comparison. The supervisor restarts using the same pinned command and MCP endpoint. The agent reconnects and inspects `describe_task.restoration`; there is no successful restoration verdict in the pre-restart response. Other checkpoint directories, immutable artifacts and earlier journal rows are not replaced. A failed staging/swap restores the old world and preserves a failed request diagnostic. A failed loaded-state comparison keeps the world frozen and forbids useful simulation until explicit repair/another restore.

Before the first useful tick, boot restores controller context and loads the exact prepared chunks while frozen. Minecraft's real readiness checks must hold. The resumed raw state, full typed NBT, ordered inventory data, queues, deadlines/priorities/sub-tick order and absolute world/time-of-day clocks are compared without normalization. Differences report `first_tick=0`, exact fields, and `different`. Equal incomplete observations report `indeterminate`. Preparation before comparison executes zero game ticks and reports its readiness/differences separately; it cannot silently repair or reset the construction. Useful simulation counters are restored from context; the journal verifier validates explicit restore clock segments without rewriting earlier rows.

The real replay proof covers the ordinary chest, lever/repeater and piston-at-rest fixture of immutable prototype #3 (`7bcdf3daaab752eef6d3f14011427c30c62f0e51`). Moving mechanisms are rejected. Hopper `last_tick_time` and arbitrary block-entity runtime remain unestablished. Torch burnout history is not serialized and therefore rejected in this checkpoint path. Chest viewers/lid/cache restart empty with no players; scheduler sub-tick counter, block events and neighbor stacks are JVM-only and must have no pending work at capture; subsequent exact order is checked by replay. Observed influence and input sampling ownership are persisted explicitly in context. Entity mechanisms, all RNG streams and universal JVM capture are outside the guarantee. These limits are provenance, not claims of door conformity.

## Implemented integration

- `Controller`: retain/checkpoint real rest evidence after `Transition.report().status=terminated`; invalidate it on state mutation, simulation or any preparation that changes coverage. Build snapshot via `Checkpoints.snapshot(Observation.raw(world), worldTime, timeOfDay)`. `create_checkpoint` invokes `Checkpoints.create(worldPath, snapshot, context, provenance, frozenIdle, () -> server.save(false,true,true))` from the serialized thread. Capture operation start/end and prove flush introduced no game tick. `restore_checkpoint` delegates request creation and rejects subsequent mutation/simulation while restart is pending. Reads/listing still work.
- Controller context schema: format/version, attempt UUID, immutable task, useful simulation/preparation counters, ordered forced chunk coordinates, ordered observation positions, input declaration **and full sampling state**, selected execution cadence/environment. Checkpoint file hashes/identity and context format are verified on boot; checkpoint owner matches the persisted attempt. Restore boot takes precedence over evidence-only artifact recovery. No `start_attempt` or fresh identity is invented.
- `Observation`: export/import ordered tracked positions and historical outside-coverage state. Do not reconstruct a smaller position set or erase missing coverage to manufacture equality.
- `Inputs`: export/import declared position, input, driver, outward/device/mode/adapter coordinates, sampling flag and last source/input power. Armed pending actions are disallowed at capture. Import should validate actual support/state without rerunning a declaration or adapter placement.
- Server lifecycle: existing loadWorld HEAD freeze applies before the restored world loads. Boot prepares persisted chunks frozen and exposes MCP only when ready and comparison has completed. Export `restoration` with checkpoint/request IDs, exact tick0 comparison, `useful_ticks_before_comparison=0`, measured preparation ticks and readiness evidence. Replay uses the issue #9 native sprint default; `stonebench.tickExecution=unit` remains the reference option.
- `McpHttp`: exposes create/list/restore schemas. The pending request is nested under `restore`, keeping the ordinary operation `status=ok`. Only after the HTTP response has been written and closed is the matching `restore-response.json` acknowledgement published. The supervisor requires matching request/response UUIDs and owns its child PID/stdin; no process discovery/global kill. If the response fails before acknowledgement, the world remains frozen and reissuing the same checkpoint ID returns the pending request so its acknowledgement can complete. A different pending restore is rejected.
- Launcher/test launcher: supervise request, stop, verify/stage/swap and restart, preserve logs per boot and old world for rollback. Restore world replacement runs with no Minecraft process alive. A fixed world path under the owned server root and canonical UUID prevent request-directed arbitrary filesystem writes.
- Build: register isolated `CheckpointChecks` runner alongside existing checks.
- Journal verifier: an explicit restore segment changes useful counters/world clock; validate old segment end, request/checkpoint identity and resumed clock rather than normalizing all journal clocks globally.

## Running the owning supervisor

`scripts/checkpoint_server.py` runs one prepared pinned server directory, with `level-name=world` under that directory. Java launcher, mod, server properties and accepted EULA must already be present. Before recovery or launch it verifies the previously recorded child has exited and opens every live/backup process lock exclusively. A live PID, uncertain ownership/liveness or held lock causes a diagnostic refusal without world replacement; production never kills a discovered PID. This also covers an orphan Java child after abrupt supervisor death. The owner must stop that child before retrying. The supervisor starts a hidden owned Java process, keeps console logs per boot, accepts `stop` on stdin (or Ctrl+C), and applies only acknowledged restore requests after waiting for child exit. A failed staging/swap retains the old world; a child startup failure restores its old-world backup. Interrupted directory swaps are recovered before any new Java process starts. This is process-crash recovery with durable transaction files and rollback paths; power-loss durability of all filesystem metadata is not claimed.

```powershell
& <python312> scripts/checkpoint_server.py --server-root <owned-prepared-server> --java <java21> --port 18765 --execution sprint
```

`--execution unit` selects the retained reference. `--test` enables disposable fixture/fault tools only. `scripts/test-server.ps1 -UseCheckpointSupervisor` exercises this same delivered launcher for two isolated servers. Its default remains sprint. Without a supervisor, create/list still work and restore is explicitly rejected. After an ordinary process restart or rollback without a resume marker, evidence recovery permits listing/restoring existing checkpoints and reading artifacts; useful simulation still remains unavailable until a valid checkpoint reprise.

The server root has one owning supervisor. An atomic exclusive `supervisor.lock` OS handle is acquired before recovery/launch and retained through child stops, swaps, boot and rollback. A second supervisor refuses without changing the first owner's world; Java does not inherit the lease. Abrupt supervisor death releases the lease, but orphan-child liveness/lock checks still apply. A durable `stonebench/child-starting.json` covers death before PID publication: ownership remains uncertain and retry is refused until the owner establishes child exit and explicitly removes that marker. Separate attempts use separate roots and ports.

## Acceptance

Use real Minecraft 1.21.11/MCP SDK 1.26.0 in the owned fresh server roots, MCP 19365/19366 and game 26181/26182, independent Gradle/runtime/world caches. Build on Java 21.0.12. Capture the prototype #3 geometry and seven diamonds, establish observed rest, create at least two immutable IDs, record the original-server continuation, then restore the chosen older ID three times. Each sequence must contain exactly 83 observations: initial, input-on, 40 tick states, input-off, 40 tick states. The production lateral input phase differs from the prototype's floor fixture; the test-only fixture must preserve the original geometry and between-tick interactions rather than changing the production input contract. Every relevant state/event/absolute-clock field is retained. Verify all other IDs and historical artifacts are still readable after every restore.

The manual-copy negative control changes only the seven-diamond NBT count to eight in the first proof observation and expects first tick 0 with the exact NBT field path. Additional controls cover rest not established, stale rest after mutation/advancement, moving piston, hopper indeterminate, unsafe IDs, corrupt world/manifest, truncated trace, chunk readiness failure, immutable IDs and process-lock recreation. Report game ticks and wall time separately. Build/pure checks alone are not evidence of faithful Minecraft reprise.
